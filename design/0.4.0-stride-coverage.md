# Design: STRIDE per element coverage (v0.4.0)

Status: proposed. Target: schema 0.4.0, rubric 0.3.0, skill 0.4.0. Depends on: the v0.3.0 baseline eval run.

## 1. Problem

PARA finds risk by searching for attack paths from an untrusted source to a sensitive sink. That search is strong for information disclosure and elevation of privilege, which is where most agent incidents land. It is structurally weak on two STRIDE categories:

- **Repudiation.** An agent acting under a human's identity with no action provenance has no source and no sink. The risk is a missing property, so there is no path to find.
- **Denial of service.** Runaway loops, unbounded sub agent spawning, and cost exhaustion need no attacker reaching a sink.

Today STRIDE appears in PARA only as a label on findings (`findings[].stride`) and as guidance in `references/stride_agentic.md`. Nothing records which element and category pairs were considered, so a reviewer cannot tell a clean result from an unexamined one.

## 2. Goals and non goals

Goals:
1. Record, for every element of the design and every STRIDE category that applies to it, whether the pair produced a finding, is mitigated by a named control, or does not apply, with a reason.
2. Give missing property findings (repudiation, denial of service) a defined tier so they are rated consistently.
3. Measure the change against the v0.3.0 baseline on the same cases, model, and run count.

Non goals:
- Replacing path search. STRIDE coverage runs after it and adds to it.
- Covering agentic classes (goal manipulation, collusion, and the rest). They stay in `agentic_class`.
- Phase two topology analysis. Section 11 notes how this carries over.

## 3. Schema 0.4.0 (additive)

Two optional top level arrays. Optional keeps every 0.3.x document valid, so this is a minor version bump.

```json
"elements": [
  {
    "element_id": "store.chat_history",
    "kind": "data_store",
    "name": "Chat transcript history",
    "refs": ["in.engineer_request"],
    "is_audit_record": true,
    "crosses_boundary": false
  }
],
"stride_coverage": [
  {
    "element_id": "store.chat_history",
    "category": "repudiation",
    "status": "finding",
    "finding_ids": ["f.no_agent_provenance"],
    "control_ids": [],
    "rationale": "Only provenance for agent actions, and engineers can delete it."
  }
]
```

Field rules:
- `elements[].kind`: `process`, `data_store`, `data_flow`, or `external_entity`. Trust boundaries are not elements; they decide which data flows need coverage (`crosses_boundary`).
- `elements[].refs`: ids elsewhere in the document this element corresponds to (inputs, capabilities, protocol peers, the subject agent id).
- `elements[].is_audit_record`: data stores only. Marks a store whose integrity is what makes actions attributable; it makes repudiation applicable to the store.
- `stride_coverage[].status`: `finding`, `mitigated`, `not_applicable`, or `not_assessed`.
- One new finding field, `findings[].finding_kind`: `path` (default, today's behavior) or `property` (no attack path; a missing property such as provenance or a spend cap). Property findings list the capabilities they affect in a new `affected_refs` array.

### Minimum elements

The assessor must create at least: the subject agent as a `process`; every input as a `data_flow` (with its source as an `external_entity` when the source is outside the trust domain); every egress capability as a `data_flow`; every memory, vector store, log, or quota the design depends on as a `data_store`; every protocol peer as a `process` or `external_entity`.

## 4. Applicability

Classic STRIDE per element, adapted for agents. The validator requires coverage for exactly these pairs.

| Element kind | S | T | R | I | D | E |
|---|---|---|---|---|---|---|
| process (agent, MCP server, peer agent inside the trust domain) | yes | yes | yes | yes | yes | yes |
| external_entity (user, third party server, outside peer agent) | yes | | yes | | | |
| data_store (memory, vector store, config, quota) | | yes | when `is_audit_record` | yes | yes | |
| data_flow (input, egress, protocol link) | | yes | | yes | yes | |

Data flows need coverage only when `crosses_boundary` is true. This keeps the matrix proportional to the design.

## 5. Rubric 0.3.0: tiering property findings

Path findings keep today's rules. Property findings get one new rule:

1. **Sink class.** Take the highest sink class (S0 to S3, rubric section 2) among `affected_refs`.
2. **Base tier.** Use the **I row** of the base matrix: S3 high, S2 moderate, S1 low, S0 low. A missing property is exposed to internal error and misuse as readily as to an attacker, which is what the I row models.
3. **Autonomy modifier.** Apply the existing modifier (rubric section 4).
4. **Cap.** A property finding alone cannot exceed `high`. `critical` stays reserved for complete attack paths. When a property finding makes a path finding worse (for example, no provenance on the exfiltration path), record it on the path finding instead.
5. **Residual credit.** Controls that restore the missing property earn credit at the step their mechanism qualifies for, regardless of category. Tamper evident action provenance counts as structural preventive for repudiation; a hard spend cap or step limit counts as structural preventive for denial of service. Prompt instructions never restore either property.

Expected results for the staged cases follow this rule: case 12 (irreversible production actions, S3) and case 13 (paid calls on a shared quota, S3) are `high` inherent.

## 6. Workflow change (SKILL.md)

Insert as step 8b, after attack path search and before tiering:

> **8b. STRIDE per element coverage.** Load `references/stride_agentic.md`. Build `elements` using the minimum element rules. For each element, consider every applicable STRIDE category from the applicability table. Record each pair in `stride_coverage`:
> - `finding` when it produces or confirms a finding. Add the category to that finding's `stride` list.
> - `mitigated` when a named control addresses it. Cite the `control_ids`.
> - `not_applicable` only when the category cannot apply to this element in this design. Give a specific reason tied to a design fact.
> - `not_assessed` when the artifacts do not say enough. Say what is missing. This is an honest gap, not a failure.
>
> Missing properties (no provenance, no spend cap, no step limit) are findings with `finding_kind: property`. Tier them with rubric section 5a.

## 7. Validator rules (scripts/validate.py)

Errors:
1. Every `elements[].refs` id resolves to an id in the document.
2. Every `stride_coverage` entry names an existing element and a category that applies to its kind.
3. When `stride_coverage` is present, every applicable pair for every element has exactly one entry.
4. `finding`: `finding_ids` is non empty, each id exists, and each named finding lists the category in `stride`.
5. `mitigated`: `control_ids` is non empty and each control exists with status other than `missing_recommended`.
6. `not_applicable` and `not_assessed`: `rationale` has at least 30 characters.
7. `finding_kind: property`: `affected_refs` is non empty and `attack_path` is empty.

Warnings:
1. An input or egress capability that appears in no element's `refs`.
2. A finding with `stride` labels that no coverage entry references.
3. More than half of the required pairs marked `not_applicable` (possible checkbox coverage).
4. A behavioral control cited as the mitigation for repudiation or denial of service.
5. A property finding tier that disagrees with rubric section 5a.

## 8. Report

The reviewer view gets a coverage matrix: one row per element, one column per STRIDE category, each cell showing the finding id, the control id, N/A, or a gap marker. Cells for pairs that do not apply are blank. This is the artifact reviewers will look at first, because it shows completeness at a glance.

## 9. Safeguards against checkbox coverage

A model can fill the matrix with `not_applicable` to finish faster. The design counters that four ways:
- `not_applicable` requires a specific rationale, and `mitigated` requires a real control id, so the fastest honest answer is often the finding.
- Validator warning 3 flags high N/A rates.
- Cases 12 and 13 are traps for exactly this: the correct answer for repudiation and denial of service on the agent process is a finding, and an N/A there scores as a miss.
- The eval report adds the N/A rate per run, so drift is visible across releases.

## 10. Evaluation plan

The point of this release is a measured difference, so the comparison has to be fair.

**Baseline.** v0.3.0 skill, model M, 5 runs per case, all 13 cases (the 11 existing cases plus 12 and 13). Cases 12 and 13 should be moved into `evals/` **before** the v0.3.0 baseline run, so the baseline shows the gap they were built to expose. The harness already scores `required_stride_categories`.

**Treatment.** v0.4.0 skill, same model, same run count, same 13 cases, same harness version.

**Metrics.**
- Recall on cases 12 and 13 (the target).
- Recall on cases 01 to 11 (must not regress).
- False positives on case 02 (must stay at zero).
- Tier agreement across runs for all three horizons.
- N/A rate in `stride_coverage`.
- Mean output tokens per assessment (from the `run_NNN.meta.json` sidecars), to report the cost of coverage honestly.

**Success criteria.**
1. Recall on 12 and 13 rises to at least 80 percent.
2. Recall on 01 to 11 drops by no more than 5 points.
3. Case 02 false positives stay at zero.
4. Tier agreement stays at or above 0.8.

**Held out check.** After any tuning against these 13 cases, write two new coverage cases that were not used for tuning, and report their results separately.

## 11. Phase two

In a topology, STRIDE runs per interaction: each edge between agents is a data flow crossing a boundary, and each agent is a process. The same `elements` and `stride_coverage` structures compose across assessments, which is one more reason to fix their shape now.

## 13. Open questions

1. Should `stride_coverage` become required in schema 1.0, or stay optional so lightweight assessments remain possible?
2. Is the I row the right base for property findings, or should repudiation and denial of service each get their own small matrix?
3. Should `not_assessed` count against recall in evals, or be reported separately as honest gaps?
4. Does the 30 character rationale minimum help, or will it just produce padded text? The N/A rate metric should answer this after one release.
